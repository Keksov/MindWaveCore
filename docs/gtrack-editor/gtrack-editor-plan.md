# gtrack-editor — новый редактор gnaural-треков на одной форме с волной и спектром

**Owner request (2026-07-08):** переработать редактор gnaural-треков так, чтобы gnaural-треки
(далее **gtrack**) были видны одновременно с волной и спектром на одной форме. Текущий
gnaural-редактор **не трогаем** — новый пишется с нуля, но с опорой на существующий код.
Сначала — новый редактор gtrack; синхронизация волнового и XML представлений — потом.

Ledger (authoritative): [gtrack-editor-progress.json](gtrack-editor-progress.json).
Методология Plan+Ledger — как в [spectrogram-fixes](../spectrogram-fixes/spectrogram-fixes-plan.md):
atomic per-step commits (префикс id шага), verify перед done, пауза на owner-чекпоинтах.

## 1. Требования владельца (дословно → нумерованно)

1. Новый редактор gtrack, старый (вкладка «Редактор»: CodeMirror XML + GnauralScheduleView)
   остаётся нетронутым.
2. gtracks видны **одновременно с волной и спектром** на одной форме.
3. Каждый gtrack может отображаться **в отдельной дорожке-редакторе**, по аналогии с
   аудио-дорожками.
4. В одной gtrack-дорожке можно отображать **один или несколько** gnaural-треков (voices)
   одновременно.
5. Режимы отображения/редактирования дорожки: **Base freq / Beat freq / Volume / Stereo balance**.
6. Если в gtrack есть **аудио-фрагменты** (voice type audiofile) — отображать их как спектр /
   волну / оба, **инлайн в дорожке самого gtrack** или **собранными в отдельной дорожке**
   редактора. То же для типа **noise**.
7. **Вершины-точки** (entries), в которых задаются параметры: режим выбора/редактирования точек
   включается и выключается; редактирование **перетаскиванием мышкой за точку** и **через диалог
   параметров выбранной точки**.
8. Фаза 2 (после базового редактора): режим **синхронизации между волновым и XML
   представлениями** — обсудить отдельно.

## 2. Что уже есть (verified 2026-07-08)

- **Модель расписания**: `GnauralScheduleData / Voice / Entry` в
  [SharedPasCore/ts/protocol.ts](../../../SharedPasCore/ts/protocol.ts) (~строка 700): voices с
  `type/typeIndex/description/hidden/muted/mono/color/audioFilePath`, entries с
  `startSec/endSec/durationSec`, `baseFreqStart/End`, `beatFreqHalfStart/End`,
  `volL/volR Start/End`. Сервер строит её через `Gnaural.exe --dump-schedule`
  (gnaural-session.ts), клиент кэширует в `stores/audio.ts` (`gnauralScheduleCache`).
- **Сохранение XML**: `server/gnaural-editor-store.ts` — атомарная запись
  (temp → валидация `Gnaural.exe --dump-schedule` → rename).
- **Рендер-мост**: `server/spectrogram-audio-source.ts` **уже** рендерит `.gnaural → WAV` для
  анализа — волна/спектр для gnaural-файла работают существующим путём.
- **Стек дорожек**: вкладка Аудио, unified track model (SF-D66): kind/channel/visible/order,
  общий time view (`spectrogramShared`), минимап, ресайзеры, глаз/драг слева, шестерёнка справа.
- **Старый редактор**: `GnauralEditorPanel.vue` (1270) + `GnauralScheduleView.vue` (3197,
  канвас-просмотр voices: hidden/muted/color, overlay/tracks, log/linear, свой минимап;
  вершины НЕ редактируются). Используем как референс отрисовки, в код не лезем.

## 3. Решения (locked 2026-07-08, Q&A с владельцем)

- **GT-D1 — новый код рядом со старым.** Новые компоненты `GTrack*` (view, диалоги, модель);
  `GnauralEditorPanel` / `GnauralScheduleView` не изменяются. Переиспользуем: протокольную
  модель, dump-schedule, gnaural-editor-store (save+validate), рендер-мост, стек дорожек SF-D66.
- **GT-D2 — хост: вкладка Аудио, общий стек.** gtrack-дорожки — новый `kind:'gtrack'` в unified
  track model; общая шкала времени/зум/пан/минимап/ресайзеры/глаз/драг/шестерёнка. Появляются
  только когда открыт `.gnaural`. *(Уточнено GT-D10: хост-стек переезжает в новую вкладку
  «Треки»; старая «Спектрограмма» замораживается.)*
- **GT-D3 — волна/спектр = рендер gnaural → WAV** (существующий механизм анализа). После Save —
  инвалидация анализа и перечитывание (перерендер по кнопке; авто-режим — опция позже).
- **GT-D4 — правки: модель в памяти + Save.** Редактируется реактивная копия расписания;
  undo/redo в памяти; dirty-флаг; Save (кнопка + Ctrl+S) сериализует и пишет через существующий
  store с валидацией.
- **GT-D5 — сохранение = патч исходного XML, не регенерация.** Дамп-модель может быть неполной
  (поля, которые `--dump-schedule` не отдаёт: типы волн, фазы и т.п.). Поэтому Save парсит
  исходный XML (DOMParser), точечно обновляет значения затронутых entries/voices и сериализует
  обратно — все неизвестные поля сохраняются. Полная регенерация — только если патч окажется
  нежизнеспособным (зафиксировать отдельным решением).
- **GT-D6 — производные оси.** Beat freq отображается как 2×`beatFreqHalf`; Volume =
  (volL+volR)/2, Stereo balance = из volL/volR; редактирование Volume/Balance маппится обратно
  в volL/volR (при mono — только volL).
- **GT-D7 — синхронизация волна↔XML — фаза 5**, отдельное обсуждение дизайна с владельцем
  до какого-либо кода.
- **GT-D8 — добавление/удаление узлов (owner req. 9).** Модель получает `insertPoint` (по времени
  клика, значения интерполируются из соседних сегментов) и `removePoint` (транзакционно, undo/redo).
  Инварианты: монотонность по времени; нельзя опустить voice ниже 1 сегмента (≥2 точек). Патчер
  GT-D5 уже регенерирует весь блок `<entries>` из точек, поэтому изменение числа точек
  сериализуется без доработок. UI (double-click — добавить, Delete/контекстное меню — удалить) — в
  фазе 3.
- **GT-D9 — prepared-узлы: отличие + фиксация (owner req. 10–11).** Проверено 2026-07-08: дамп
  РАЗВОРАЧИВАЕТ `<entry type="preparse">` в конкретные точки (circle.gnaural → 60 entries / 61
  точка на voice), но в исходном XML остаётся один generator-узел. Дамп сам по себе НЕ помечает
  происхождение, поэтому voice-и с preparse определяются **разбором исходного XML** (id тех voice,
  где в `<entries>` есть `type="preparse"`). Такие точки в модели помечаются `preparse: true`.
  (10) Рендер: prepared-точки рисуются **иначе** (напр. полые/пунктирные маркеры) + бейдж
  «generated» на дорожке. (11) Фиксация: явное действие «Зафиксировать / сделать редактируемым» на
  voice снимает флаг (in-memory «запекание» разворота в регулярные точки) → точки становятся
  редактируемыми; до фиксации прямое редактирование prepared-точек заблокировано (попытка —
  предложить зафиксировать). На Save зафиксированный voice пишется конкретными entries (уже GT-D5).
  Фиксация необратима в рамках файла (теряется связь с генератором) — предупредить пользователя.
- **GT-D10 — вкладка «Треки», старые вкладки заморожены (owner req. 12, Q&A 2026-07-08).**
  Выбран **вариант 1 — «замороженная копия»**: (a) новый компонент `TracksPanel.vue` — **перенос
  текущего стека** (волна + спектр + минимап + gtracks + вся обвязка SF25–28/GT2.2) из AudioPage;
  саб-вкладка «Треки» справа от «Спектрограммы»; (b) вкладка «Спектрограмма» **восстанавливается
  из git** до состояния перед GT2.2 (`GnauralCore 6c0589c`) — остаётся ровно принятой, без
  gtracks; «Воспроизведение» не менялась. Направление переноса: старое — из git, текущий код
  (= старое + новое) — в TracksPanel; пере-дописывать новое в старую копию не нужно.
  **Область:** «Треки» работает для **всех аудиофайлов** (gtracks — только для .gnaural) и
  становится единой поверхностью будущего редактора; весь дальнейший функционал (Phase 3+) — только
  там. **Изоляция:** полностью раздельное состояние — свой zoom/selection (`provide` в TracksPanel)
  и **свои localStorage-ключи** (высоты/цвета/раскладка/линзы), никаких взаимных влияний со старой
  вкладкой. Цена: осознанное дублирование (~400 строк шаблона + логика); фиксы вносим только в
  «Треки», старые вкладки заморожены и после стабилизации будут удалены.
- **GT-D11 — управление файловым кэшем (owner req. 13, 2026-07-09).** Сервер кэширует рендеры
  gnaural→WAV (`tmp/audio-render`, в т.ч. новый `single-loop`-вариант для спектра) и конверсии
  (`tmp/audio-convert`). Ключ кэша — sha1(путь+size+mtime+kind+discriminator), т.е. **обратного
  сопоставления cache→исходник нет**. Поэтому нужен **манифест** (при записи в кэш сохранять
  `{cacheFile, sourcePath, kind, discriminator, bytes, createdAt}` в `tmp/audio-cache-manifest.json`
  или sqlite). UI (на вкладке «Треки» или в настройках): **общий размер**, список **по исходному
  файлу** с размерами и вариантами (render full / render single-loop / convert), **удаление**
  записи и **очистка всего**; действия — через новые эндпоинты (`GET /api/audio/cache`,
  `DELETE /api/audio/cache?...`). Осиротевшие файлы (без манифеста, от старых сборок) — показывать
  отдельной группой «неизвестный источник» с возможностью удалить.

  (2) **щелчок на стыке цикла** (`loops>1` или `0`) — громкость конца ≠ громкости начала голоса;
  (3) **вырожденные хвосты** — последний узел `duration≈0` (CandyWreck, SummerSunshine 1e-13) и
  пачки нулевых узлов подряд;
  (4) **несогласованный `entrycount`/`totalentrycount`** с фактическим числом узлов;
  (5) **отсутствующие файлы** audiofile-голосов (pcm без файла на диске);
  (6) денормалы/экстремальные значения (Penfold 4e-70).
  Реализация: чистый TS-модуль `gtrack-lint.ts` (модель → список diagnostics {rule, voiceId,
  severity, message, at}) + bun-тесты; UI — панель/бейдж на «Треках» со списком проблем, клик =
  переход к месту; авто-фиксы (напр. «добавить фейд») — отдельными действиями с подтверждением.
  Фейд-механика для авто-фикса уже отработана скриптом: последний узел (D−f)+hold(f)+zero(0), для
  вырожденных хвостов — заём f у ближайшего длинного узла назад; позиционные замены (не строковые).

## 5. Риски

- **R1 — полнота патча XML (GT-D5).** Соответствие entry в дампе ↔ узла в XML (индексы,
  overallVol, loops). Проверяется round-trip'ом в GT1.2 до любого UI.
- **R2 — инвалидация анализа после Save.** Кэш анализа ключуется путём+параметрами — после
  перезаписи файла нужен принудительный re-open/перерендер (mtime в ключе или явный сброс).
- **R3 — ось времени при loops.** `totalTimeSec` расписания vs длительность отрендеренного WAV
  (loopCount>1): выравнивание шкалы gtracks и волны/спектра.
- **R4 — noise-фрагменты.** У noise нет файла; вол/спектр для него = либо рендер соло-voice
  через gnaural (дорого), либо синтетическое превью. Решить в GT4.1.
- **R5 — производительность канваса** при многих voices × many entries — рисовать по
  видимому окну (как SpectrogramView), не всю схему. Актуально и для prepared-voice (circle → 61
  точка/voice; несколько voice-ов).
- **R6 — необратимость фиксации prepared-voice (GT-D9).** «Запекание» разворота в конкретные
  entries теряет generator-узел `<entry type="preparse">` в файле — вернуть генератор нельзя.
  Предупреждать пользователя; фиксация — только по явному действию, не автоматически.
- **R7 — дублирование стека (GT-D10).** «Треки» = копия стека; баг-фиксы вносим ТОЛЬКО в
  TracksPanel — старые вкладки заморожены (не чинить, кроме критики). После стабилизации «Треков»
  старые вкладки удаляются отдельным шагом (внести в план тогда). Держать перенос механическим
  (без попутных правок), чтобы diff был проверяемым.
- **R8 — большие исходные файлы (owner вопрос 2026-07-09).** `singleLoop`-кап помогает ТОЛЬКО
  gnaural с повторами. Настоящая многочасовая запись без loop-ов: (а) **клиент** сейчас качает весь
  файл + `decodeAudioData` → 2ч стерео 48к ≈ 2.7 ГБ в памяти вкладки → OOM. Это чинит **Phase 7**
  (клиент перестаёт декодировать, тянет только тайлы+пики по окну — размер исходника перестаёт
  влиять на браузер). (б) **Бэкенд** грузит весь канал в память (`FSamples`, ~1.4 ГБ/канал на 2ч) и
  считает STFT по всему — сервер переживёт больше браузера, но для очень длинных файлов это тоже
  потолок. Полное решение — **потоковый/оконный STFT** на воркере (читать окна через `Seek`, не
  держать весь канал; seek-путь `LoadChannelSamples` уже есть). Отдельная бОльшая работа, не в
  Phase 7 — кандидат в новый шаг после завершения тонкого клиента.
