# tracks-playhead — плейхед и многопетлевые файлы на вкладке «Треки»

**Owner request (2026-07-15/16):** возник из разбора «почему Play заново считает спектрограмму».
По ходу выяснилось, что на **многопетлевых** .gnaural (loops > 1) вкладка «Треки» показывает ось
длиной в **одну петлю**, а плейхед при воспроизведении едет по **всей сессии** — и на файлах вроде
CricketsAndFrogs (0.79 с × 8000 = 6303 с) улетает за край мгновенно, вкладка бесполезна. Владелец
предложил переиспользовать уже посчитанную одно-петлевую спектрограмму (тайлинг). После замеров
принят **план B** (см. TP-D1): показывать одну петлю (все петли идентичны — показывать нечего),
плейхед цикличный, плюс индикатор петли. Предварительное условие производительности —
[TP-D2] вынести плейхед на отдельный канвас.

> **ПОПРАВКА 2026-07-16 (TP-D4):** исходная посылка «плейхед едет 0…fullDuration и улетает за
> одно-петлевую ось» **неверна** (моя ошибка — выведена из формулы длительности, не сверена с путём
> позиции). По коду GnauralSynth позиция **loop-local** (обнуляется на каждой петле), и владелец
> подтвердил на waves.gnaural: курсор циклится 0…40…0, статус-бар согласован. Следствие: вкладка уже
> отрабатывает многопетлевые файлы; TP2.2 (mod) — no-op → пересобран в «индикатор петли»; TP2.3 —
> не баг → снят. Остаётся мелочь: номер петли (gnaural знает `FcurrentLoop`, но не шлёт) и заикание
> субсекундных петель (TP3.1). Подробности — TP-D4 в ledger.

Ledger (authoritative): [tracks-playhead-progress.json](tracks-playhead-progress.json).
Методология Plan+Ledger как в [gtrack-editor](../gtrack-editor/gtrack-editor-plan.md): atomic
per-step commits (префикс id шага), `verify` перед `done`, owner-PAUSE на визуальных чекпоинтах.

## 1. Требования владельца (суть треда → нумерованно)

1. Многопетлевые .gnaural должны нормально работать на «Треки»: плейхед обязан **соответствовать
   тому, что реально звучит**, а не улетать за край на первой же секунде.
2. Не восстанавливать полный многопетлевой рендер ради этого — он ровно то, чего избегает кап
   `<loops>1</loops>` (6303 с стерео ≈ 1.1 ГБ WAV, браузер не декодирует).
3. Идея владельца: переиспользовать уже посчитанную (одно-петлевую) спектрограмму, «подставляя её в
   нужные места» (тайлинг). → рассмотрено, отклонено в пользу плана B (TP-D1).
4. Движение курсора не должно быть дорогим (владелец сам поднял вопрос о нагрузке CPU и предложил
   адаптивность). → плейхед на отдельном канвасе (TP-D2); частота прогресса — адаптивно (TP3.1).

## 2. Что уже есть (verified 2026-07-15/16)

- **Стек «Треки» одно-петлевой и внутренне согласованный.** Кривые голосов меряются
  `gtracks.durationSec = schedule.totalTimeSec` (одна петля); волна/спектр — `spectrogramDuration =
  backendAnalysis.durationSec`, где сервер форсит `<loops>1</loops>` в
  [spectrogram-audio-source.ts:60-69](../../../GnauralCore/server/spectrogram-audio-source.ts#L60-L69);
  статус-бар — тот же `spectrogramDuration`. Всё выровнено по времени в одной колонке.
- **ИСПРАВЛЕНО (TP-D4):** ~~позиция плейхеда сессионная (0…полная длительность)~~ — на самом деле
  **loop-local** (0…loopDur). GnauralSynth обнуляет `FcurrentSampleCount` на каждой петле
  ([GnauralSynth.pas:428](../../../GnauralCore/cli/core/GnauralSynth.pas#L428)),
  `getPlaybackPosition = FcurrentSampleCount/rate`, ниже никто не аккумулирует. Поэтому плейхед и
  статус-бар уже согласованы с одно-петлевой осью. `FcurrentLoop` считается в синте, но клиенту не
  отправляется.
- **Длительность воспроизведения** сервер считает как `totalTimeSec × max(1, loopCount)`
  ([gnaural-session.ts parseLoadedEvent](../../../GnauralCore/server/gnaural-session.ts)).
- **`loopCount` есть в протоколе** ([protocol.ts:850](../../../SharedPasCore/ts/protocol.ts#L850)),
  но в `use-gtrack-lanes.ts` / `TracksPanel.vue` на клиенте **не используется**.
- **Многопетлевые файлы реальны.** Замер по 296 preset-файлам: ~30 с `loops > 1`, максимум **8000**
  (CricketsAndFrogs, петля 0.79 с → 6303 с), **4900** (AndromedaHell, 1.0 с), 1000 (DesertWind
  5.8 с; Penfold 2.2 с), плюс 100/99/57/15/10/2.
- **Gnaural шлёт `playback_progress` раз в секунду** (эмит только при смене `Trunc(sec)`,
  [GnauralApp.pas](../../../GnauralCore/cli/core/GnauralApp.pas)); при этом управляющий цикл уже
  тикает каждые **100 мс** — потолок частоты без переделки цикла = 10 Гц, «считать чаще» не нужно,
  дорого только «писать чаще».
- **Рендер тела дорожки — дорогой.** `draw()` спектра пересчитывает RGBA каждого видимого тайла
  попиксельно (`tileToImage`, без кэша) и реблитит; GTrackView вдобавок реаллоцировал канвас
  (`canvas.width = …`) на каждом тике. До TP1.1 это гонялось на **каждое** движение плейхеда.

## 3. Решения

- **TP-D1 — план B (одна петля + цикличный плейхед), НЕ тайлинг.** Все петли идентичны по звуку, а
  спектрограмма — это магнитуда STFT: показывать сверх одной петли нечего. Тайлинг на экстремальных
  файлах даёт кашу из субпиксельных полосок (8000 петель по 0.15 px), а чтобы ось совпала с кривыми
  голосов, пришлось бы ретаймить **весь** стек (кривые + волна + спектр в одной колонке). План B
  сохраняет согласованность стека. Цена B: клик перематывает **в пределах текущей петли** (сессионную
  ось не выражает — но её показывает статус-бар).
- **TP-D2 — плейхед на отдельном оверлейном канвасе.** Замер: движение курсора иначе перерисовывает
  тело; на спектре — попиксельный пересчёт всей картинки. Оверлей `pointer-events:none` над телом;
  общий `plotGeometry()` — единственный источник геометрии, чтобы канвасы не разъезжались. `<canvas>`
  — замещаемый элемент: `inset:0` его НЕ растягивает (остаётся 300×150), нужен явный `width/height:
  100%`.
- **TP-D3 — частота прогресса адаптивна к расписанию, в Паскале.** Цель ~20 обновлений на петлю,
  зажатая в `[100 мс … 1 с]`. Тогда 223 одно-петлевых файла и длинные расписания = как сегодня (1 Гц);
  цена платится только на коротких петлях, ради которых всё и делается. Интервал считается один раз
  при загрузке (`totaltime`/`loops` известны), без логики в UI. После TP-D2 клиентская цена частоты
  почти нулевая, так что ограничитель — именно троттлинг эмита в Паскале.

## 4. Шаги

### Фаза 1 — производительность (предусловие)
- [x] **TP1.1 — Плейхед на отдельном оверлейном канвасе (GTrackView / SpectrogramView /
  WaveformView).** Движение курсора не трогает тело. Общий `plotGeometry()`; гейтинг данных сохранён.
  Коммит `5d0135b`. Owner-confirmed.

### Фаза 2 — многопетлевой плейхед
- [x] **TP2.1 — Протянуть `loopCount` (и длину петли) до стека «Треки».** `use-gtrack-lanes` теперь
  отдаёт `loopCount` и `fullDurationSec = durationSec × loopCount` рядом с неизменной одно-петлевой
  `durationSec`; доступно как `gtracks.loopCount` / `gtracks.fullDurationSec`. Дамп несёт реальные
  петли (одну петлю форсит только рендер спектра, не расписание). Поведение не изменилось. Коммит
  `8abfe1d`.
- [x] **TP2.2 (пересобран, TP-D4) — Индикатор «петля N / M».** Синт отдаёт `getCurrentLoop`,
  `playback_progress` несёт `loop`, сервер парсит, стор — `audio.currentLoop`, статус-бар показывает
  «Петля N / M» при `loopCount > 1`. Коммиты `4c5428c` (+ протокол `c0512b0`).
- [x] ~~**TP2.3 — Починить статус-бар.**~~ **Снят (TP-D4): не баг.** Позиция loop-local ≤ одной петли,
  статус-бар уже согласован. Актуально только если позже захотим явный **сессионный** readout
  (позиция / полная длительность) — тогда завести отдельно.

### Фаза 3 — плавность на коротких петлях (опционально)
- [x] **TP3.1 — Адаптивная частота `playback_progress` в Gnaural.exe (Паскаль).** Эмит по приросту
  позиции (`TotalTime/20`, clamp `[0.1с…1с]`), а не по целым секундам; на первый тик и на обороте
  петли. Управляющий цикл и так тикает 100 мс — дороже только запись, не CPU. Коммит `4c5428c`.

**Побочно (TP-D5):** во время проверки TP2.2/TP3.1 найдена и исправлена регрессия — соло-дорожка
спектра перерисовывалась на каждый тик плейхеда (deep-watch на `props.analysis` срабатывал на новую
ссылку того же содержимого → reconfigure → refetch → полный перерис). Фикс: следить по содержимому
(`JSON.stringify`). Коммит `65ba9c6`.

## 5. Риски

- **Экстремальные файлы (8000 петель).** Даже цикличный плейхед при 1 Гц скачет ~1.27 петли/тик —
  осмысленным становится только с TP3.1. TP2.2 без TP3.1 полезен на 2–100 петлях, но не на 8000.
- **Регресс одно-петлевых файлов** (223 из 296). Ось и плейхед на `loops` = 1 обязаны выглядеть как
  сегодня — проверять на обычном файле в каждом шаге фазы 2.
- **Замещаемый `<canvas>`** (уже поймано в TP1.1): `inset:0` не растягивает — только явные
  `width/height`. Держать в уме при любых новых канвас-слоях.

## 6. Верификация (каждый шаг)

Из `MindWaveCore/ui`: `bun run typecheck` + `bun run build`. Из `GnauralCore`:
`bun test ui server`. Ручная owner-проверка на **многопетлевом** файле (CricketsAndFrogs /
AndromedaHell) **и** одно-петлевом (не изменился). Серверные/Паскаль-правки — полный рестарт AppCore
(HMR их не берёт, см. [[bun-watch-ignores-cross-repo-server]]).
