# undo-branch-merge — point-дельты (go 3) + мердж веток (go 4)

Кандидат №4 из финального отчёта `undo-versioned-log`, объединённый по решению владельца с
кандидатом №3: сначала стабильные id точек и point-level дельты (фундамент), затем трёхсторонний
мердж отменённых веток в текущую линию. Ветки уже видимы/восстановимы/удаляемы
(`undo-orphan-branches`, принята 2026-07-22); мердж — недостающая операция «соединить работу
двух линий».

## 1. Требования владельца (дословно)

1. (2026-07-22) «go 4» — старт кандидата №4: «Ветки/метки/мерджи как полноценная git-модель —
   модель данных (parent-цепочка, refs, теги) уже готова» / «полноценные ветки/мерджи над моделью
   данных».
2. Квиз BM0.1 (2026-07-22), «Скоуп»: **«Сначала go 3 (point-id)»** — сперва стабильные id точек и
   point-level дельты, затем мердж на уровне точек.
3. Квиз, «Мердж»: **«Squash одним коммитом»** — итог мерджа = одна обычная правка kind='merge',
   откатывается Ctrl-Z, схема лога не меняется.
4. Квиз, «Конфликты»: **«Диалог выбора»** — перед мерджем список конфликтов, для каждого выбор
   «моя версия / из ветки»; бесконфликтное сливается молча.
5. Квиз, «После»: **«Оставить лежать»** — ветка после успешного мерджа остаётся в списке
   (принцип «записи живут, пока я сам не почищу»); удаление — существующей кнопкой.
6. (2026-07-22, приёмка BM1.4: «Всё проверил, всё работает без ошибок!») «При открытии журнала,
   в котором есть ветки, иконка в тулбаре отображается синей, но ветки не видны. Нужносделать
   так, что как только в списке появляется ветка, она сраху отображается и иконка отображается
   синей. При открытии иконка должна соответствовать налчию веток в журнале, если они есть, то их
   надо сразу показывать».
7. (там же) «Очистить всю истоию - показывать сообщее, что это невозможно отменить и запрашивать
   подтверждение Да/Нет».

## 2. Контекст (разведка)

- Шаг undo сегодня: `GTrackVoiceDelta {voiceId, before: GTrackVoice, after: GTrackVoice}` — голос
  ЦЕЛИКОМ до/после (gtrack-model.ts:210). На голосе в сотни точек одноточечная правка тащит весь
  голос дважды — отсюда ценность point-дельт (размер) и точность мерджа.
- Голоса правками не создаются/не удаляются (UC-D6), у голосов стабильный числовой id — мердж
  оперирует составом голосов безопасно.
- Точки: `GTrackPoint {timeSec, baseFreq, beatFreqHalf, volL, volR}` без id; строятся из N
  сегментов как N+1 контрольных точек (`segmentsToPoints` :66: старты всех + конец последнего);
  `toSchedule()` (:857) конвертирует обратно в `GnauralScheduleData` — формат снапшотов лога.
- Сигнатуры = `JSON.stringify` расписания (:203) — любые новые поля меняют их: нужна
  id-инвариантность, иначе старые снапшот-якоря перестанут сходиться (адопция, S9).
- Реконструкция состояния любого cid уже есть (checkoutUndoCommit), развилка ветки — в сводке
  (`branch.forkParent`), «правка одной транзакцией» — `replaceVoicePoints` + `edit(kind)`.

## 3. Решения

- **BM-D1 (порядок).** Двухфазная фича: Фаза 1 = go 3 (id + point-дельты), Фаза 2 = мердж.
  PAUSE-приёмка после каждой фазы: point-дельты меняют ядро редактора, владелец проверяет его
  стабильность до постройки мерджа сверху.
- **BM-D2 (идентичность точек).** `GTrackPoint.id: string` — генерация с сессионной энтропией
  (как step.id/cid: уникальность сквозь форки и рестарты). Файл `.gnaural` НЕ меняется: id живут
  в памяти и в ЛОГЕ — дельты ссылаются на id, снапшоты несут расписание с id через ОПЦИОНАЛЬНЫЕ
  поля `GnauralScheduleEntry` (protocol; сервер контент-агностичен, VL-D1). N сегментов ↔ N+1
  точек: id точки i — в entry i (поле pointId), id последней точки — отдельное опциональное поле
  голоса (lastPointId). Загрузка файла без лога/якоря → свежие id; адопция со снапшота с id →
  id продолжаются.
- **BM-D3 (сигнатурная инвариантность).** Все сигнатуры (model.signature,
  scheduleContentSignature) вычисляются по расписанию БЕЗ id — старые снапшоты и файловые
  состояния сходятся как раньше; эквивалентность реконструкции (S9) не затрагивается.
- **BM-D4 (шаги и совместимость).** Новая форма дельты шага: по голосам только изменённые точки
  {id, before|null, after|null} (null = вставка/удаление). Старые voice-дельты остаются
  читаемыми НАВСЕГДА: undo/redo/checkout/adoption/deep/ветки работают на смешанных цепочках;
  ретрофита старых логов нет (append-only). Панельный дифф (describeStepChanges) переводится на
  id — точный и без позиционных догадок.
- **BM-D5 (мердж, квиз).** Three-way от развилки: base = состояние forkParent, ours = текущая
  модель, theirs = верхушка ветки (реконструкция обоих — checkout-механикой). Сравнение
  point-уровнево по id; ветка/база без id (legacy) — голос-уровнево. Правила: менялась одна
  сторона → берём её; обе одинаково → ничего; обе по-разному → конфликт в диалог («моя / из
  ветки», по точке; legacy — по голосу). Применение — ОДНА транзакция kind='merge'
  (replaceVoicePoints по затронутым голосам), Ctrl-Z откатывает целиком. Ветка остаётся; ветка с
  graft-корнем (forkParent=null → base недоступен) — отказ с сообщением.
- **BM-D6 (спека-как-тесты).** Раздел 4 (P1..P5, M1..M5) — критерий приёмки кодовых шагов; fuzz
  не расширяется (мердж — чистый клиент): юниты планировщиков + конформанс E2E; UI — владелец на
  PAUSE.
- **BM-D7 (приёмка BM1.4, репорт №3).** Восстановление ПОЗИЦИИ ВЫХОДА: после адопции курсор
  доводится реплеем undo/redo до позиции head-ref (место, где сессия закончилась), а не остаётся
  на якоре — выход в середине журнала без сохранения возвращает ровно туда (несохранённые правки
  снова видны, dirty до сохранения). Head вне окна → остаёмся на якоре. Диагностика репорта: сам
  «весь журнал серый» оказался следствием очистки лога (Clear в 13:28, seq с 1) — без сохранений
  якорь = baseline; поведение якоря корректно, но ожидание позиции выхода реализовано как фикс.

## 4. Спецификация

Фаза 1 (point-дельты):
- **P1 (идентичность).** id уникален в пределах голоса и стабилен сквозь правки/undo/redo/
  save/снапшот/рестарт (через лог); вставка даёт новый id, удаление+undo возвращает прежний.
- **P2 (сигнатуры).** Сигнатуры не зависят от id: модель с id и её id-less проекция дают одну
  сигнатуру; адопция старых (без id) снапшотов работает.
- **P3 (размер).** Дельта-шаг несёт только изменённые точки; на голосе из 200 точек одноточечная
  правка даёт payload на порядок меньше voice-дельты (тест с порогом).
- **P4 (совместимость).** Смешанная цепочка (старые voice-дельты + новые point-дельты):
  undo/redo, реконструкция checkout, адопция, deep-строки и панельный дифф работают.
- **P5 (файл).** Сериализация в `.gnaural` байт-идентична прежней (id не пишутся в XML);
  препарс/воспроизведение не затронуты.

Фаза 2 (мердж):
- **M1 (чистый мердж).** Непересекающиеся изменения сторон сливаются без вопросов; результат =
  композиция (тест: ветка двигала точку A, линия — точку B → обе применены).
- **M2 (конфликт).** Точка, изменённая обеими сторонами по-разному (legacy: голос), попадает в
  диалог; выбор применяется точно; «моя» = точка остаётся как в ours.
- **M3 (squash).** Ровно один коммит kind='merge'; Ctrl-Z возвращает состояние до мерджа; лог
  append-only, ветка нетронута и остаётся в списке.
- **M4 (legacy).** Ветка со старыми voice-дельтами мерджится голос-уровнево тем же диалогом.
- **M5 (нет базы).** forkParent=null (graft) или недоступный снапшот-якорь → отказ с понятным
  сообщением, ничего не изменено.

## 5. Шаги

Фаза 0: **BM0.1** план+леджер+квиз (docs-коммит).

Фаза 1 — point-дельты (go 3), GnauralCore + SharedPasCore:
- **BM1.1** id в ядре: `GTrackPoint.id`, генерация (segmentsToPoints/insertPoint/fix-preparse),
  id-less сигнатуры, `toSchedule()` с id через опциональные поля протокола
  (GnauralScheduleEntry.pointId / voice.lastPointId), XML-путь не затронут. Юниты P1/P2/P5.
- **BM1.2** point-дельты шагов: новая форма voices-дельты (изменённые точки по id), сбор в
  транзакции, undo/redo применение по id, describeStepChanges на id; чтение старых voice-дельт.
  Юниты P3/P4 (+ размер-тест).
- **BM1.3** транспорт/лог: stepToCommitInput/commitToStep обеих форм; конформанс на смешанной
  цепочке; полные сьюты + vue-tsc + build; CRLF lanes.
- **BM1.4 PAUSE**: владелец гоняет редактор/журнал/checkout/ветки на живом wakeup (старые
  дельты) и на свежих правках (новые дельты).
- **BM1.5** пожелания приёмки (req 6/7): иконка веток = индикатор наличия (синяя ⇔ ветки есть),
  сводки грузятся сразу при готовности лога и после форка (без ленивости — и при закрытой
  панели), в нижнем режиме секция авто-раскрывается при появлении веток; «Очистить всю историю» —
  диалог подтверждения «нельзя отменить, Да/Нет» (Quasar Dialog).

Фаза 2 — мердж, GnauralCore:
- **BM2.1** чистый планировщик `planBranchMerge` (base/ours/theirs, id-уровень + legacy
  fallback, список конфликтов) + применение выборов. Юниты M1..M5.
- **BM2.2** UI: «Влить в текущую» на строке ветки (нижняя секция + inline), диалог конфликтов,
  одна транзакция kind='merge', notify итога, обновление списка веток; i18n ru/en.
- **BM2.3** конформанс E2E мерджа (реальная сессия: форк → merge → эквивалентность; legacy-ветка).
- **BM2.4 PAUSE** финальная приёмка.

## 6. Риски

- Главный: сигнатурная инвариантность (BM-D3) — ошибка ломает адопцию существующих логов.
  Страховка: P2-юниты на старом снапшоте + конформанс на wakeup-подобной цепочке.
- Маппинг id при N↔N+1 (последняя точка) — отдельные юниты на края (пустой голос, один сегмент).
- Объём правок ядра (52 модельных теста обязаны остаться зелёными или быть осознанно обновлены).
- use-gtrack-lanes.ts — CRLF; server.ts не трогается вовсе (сервер в этой фиче не меняется).
