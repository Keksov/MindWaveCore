# undo-journal-row-actions — план

Диалог доступных действий по клику на записи журнала Undo.

## 1. Требования владельца (дословно)

1. > «Добавь новую вичу в журнал Undo: при клике по записе нужно показывать диалог возможных
>    действий с этой записью»

### Уточнения (квиз owner, 2026-07-23)

2. **Схема:** «Диалог + панель остаётся» — клик открывает диалог действий, но нижняя панель
   («Применить», метки, «Очистить») продолжает работать как сейчас.
3. **Состав действий:** «Применить, Метки, Очистить журнал до этой записи, Показать изменения» —
   все четыре.

## 2. Что есть сейчас

Панель — [UndoJournalPanel.vue](../../../GnauralCore/ui/components/UndoJournalPanel.vue).

**Клик по строке ничего не делает, кроме выделения.** `selectRow(cursor)` /
`selectDeepRow(cid)` ставят `pendingTarget` / `pendingDeepCid` (подсветка). Это осознанное решение
UG3.1 (треб. 8): *«состояние двигается ТОЛЬКО кнопкой „Применить“, никогда по клику строки»* —
двухшаговая схема защищает от случайного отката.

Действия над записью сегодня разбросаны по трём местам нижней панели:

| Действие | Где сейчас | Реализация | Условие доступности |
|---|---|---|---|
| Применить | кнопка справа внизу | `applyRollback()` → `rollbackToCursor(target)` для оконных строк, `checkoutUndoCommit(cid)` для глубоких/веточных | `pendingDeepCid !== null` **или** (`pendingTarget !== null` и `!== undoCursor`) |
| Метки | кнопка `sell` → `q-menu` | `gtracks.setUndoTag(name, cid)` / `deleteUndoTag(tag)`, список из `selectedCidTags` | `selectedCid !== null` |
| Очистить до записи | пункт «Старше выделенного» в `q-btn-dropdown` | `clearBeforeSelection()` → `clearUndoHistory('before', target)` | `pendingTarget !== null` и `!== 0` |
| Изменения (дифф) | всплывающая подсказка при наведении | `item.row.changes` = `describeStepChanges(step, 8)` | `changes.length > 0` |

Типы строк: **оконные** (`deepCid === null`, есть `cursor`), **глубокие** (`deepCid !== null` —
старше окна истории, живут только в логе) и **веточные** (шаги заброшенных веток, используют тот же
`pendingDeepCid`). Строки-разделители, «Ранняя история…» и заголовки веток — не записи, диалог для
них не открывается.

## 3. Решения

- **RA-D1** — диалог **дополняет** нижнюю панель, не заменяет (owner, уточнение 2). Панель не
  трогаем вообще: нулевой риск регрессии в уже принятых сценариях, диалог — просто более удобный
  путь к тем же действиям.
- **RA-D2** — клик **и открывает диалог, и выделяет** строку, причём выделение теперь
  **не переключающееся**. Инвариант UG3.1 треб. 8 сохраняется: сам по себе клик состояние не
  меняет — «Применить» внутри диалога остаётся явным вторым шагом. Изменение против текущего
  поведения: раньше повторный клик по выделенной строке снимал выделение (`selectRow`/`selectDeepRow`
  были toggle). С диалогом это теряет смысл — сняв выделение, пользователь всё равно получил бы
  открытый диалог, но уже без цели для «Применить». Поэтому клик всегда выбирает свою строку, и
  диалог с нижней панелью гарантированно работают с одной и той же записью.
- **RA-D3** — механизм = всплывающая панель **внутри того же файла**, не `Dialog.create`: нужен
  богатый контент (список меток с полем ввода, дифф), а не текст + две кнопки. Изначально был
  `<q-dialog>` + `<q-card>` по образцу диалога слияния; заменён на `<q-menu>` — см. **RA-D8**.
- **RA-D4** — **новой бизнес-логики нет**. Все четыре действия переиспользуют существующие функции
  (`applyRollback`, `setUndoTag`/`deleteUndoTag`, `clearUndoHistory('before')`, `row.changes`).
  Диалог — исключительно точка входа; условия доступности выносятся в общие `computed`, чтобы
  диалог и нижняя панель не разъехались.
- **RA-D5** — недоступные действия **показываются в disabled-виде**, а не скрываются: пользователь
  видит полный набор возможностей записи. Пояснение «почему нельзя» — нативным `title` на обёртке
  (AGENTS.md, стандартное исключение 2: на `disabled`-кнопке тултип не может показаться).
- **RA-D6** — **диалог рендерится только когда открыт** (один экземпляр на панель, а не по одному
  на строку). Прямое следствие только что закрытого расследования undo-log-perf: `app-tooltip` на
  каждой строке стоил 10–20 мс на строку и был главной причиной тормозов журнала. Повторять эту
  ошибку нельзя — на строках не появляется НИ одного нового компонента.
- **RA-D7** — изменения показываются **внутри той же всплывающей панели**, а не вторым окном. Дифф
  берётся из уже посчитанного `row.changes` (ничего не пересчитывается). Существующая всплывающая
  подсказка при наведении остаётся — owner её убрать не просил.
  *Уточнено на приёмке RA1.7:* дифф идёт **сразу после заголовка записи** и виден **целиком** —
  не как сворачиваемый пункт «Показать изменения» и без собственного скролл-бокса. Ограничение
  высоты лежит на самой панели (`max-height="80vh"`), чтобы экстремальная запись не вылезла за
  пределы экрана.
- **RA-D8** *(приёмка RA1.7, owner: «диалог нужно открывать рядом с текущей записью, а не в центре
  экрана»)* — механизм = **`<q-menu>` с `:target`**, привязанный к DOM-элементу строки, а не
  `<q-dialog>`. Причина техническая: `QDialog` в Quasar всегда центрирует свою карточку по экрану и
  произвольного позиционирования не поддерживает; `QMenu` умеет якориться к элементу (`anchor`/`self`/
  `offset`) — и это тот же контрол, на котором уже построено меню меток этой панели. Элемент берётся
  из `event.currentTarget` в обработчике клика; Vue патчит строку по месту (тот же `:key`), поэтому
  ссылка остаётся живой. Побочный плюс: закрытие по клику вне и по Esc — бесплатно, отдельная кнопка
  «Закрыть» не нужна.
- **RA-D9** *(приёмка RA1.7)* — порядок пунктов: **Применить → Очистить журнал до этой записи →
  Метки**. «Метки» последние по прямому указанию владельца.
- **RA-D10** *(приёмка RA2.5, баг «третий клик по той же строке не открывает попап»)* — на `QMenu`
  ставится **`no-parent-event`**, а переключение открыт/закрыт реализуется **нашим** обработчиком.
  Причина прочитана в исходнике Quasar, а не угадана: `use-anchor.js:135` вешает на элемент-якорь
  собственный слушатель `click → toggle`, поэтому одним состоянием видимости управляли два
  независимых механизма. Клик 2: наш обработчик ставит `true` (без изменения), затем toggle прячет →
  закрыто. Клик 3: наш обработчик показывает, toggle тут же прячет обратно → «не открывается».
  Клик по другой строке «чинил» это лишь потому, что слушатель-якорь оставался на предыдущей строке.
  Конфликтовать после отключения нечему: `click-outside.js` исключает клики внутри якоря
  (`anchorEl.contains(target)`), т.е. клик по строке никогда не считался «кликом вне».
  Смена строки при открытом попапе делается через закрыть → `nextTick` → открыть, чтобы он не
  остался спозиционированным по прежнему якорю.
- **RA-D11** *(приёмка RA2.5)* — у попапа есть **футер с кнопкой «Закрыть»** (`v-close-popup`), хотя
  закрытие по клику вне и по Esc работает и без него — по прямому указанию владельца.

  глубокой, веточной), общие `computed` условий доступности, действие «Применить», кнопка «Закрыть».
- **RA1.3** — «Метки»: список меток записи + добавление/удаление прямо в диалоге.
- **RA1.4** — «Очистить журнал до этой записи» (с подтверждением — операция необратима).
- **RA1.5** — «Показать изменения»: раскрывающийся дифф из `row.changes`.
- **RA1.6** — verify: `bun test ui server`, `vue-tsc`, `quasar build` + проверка по логу

## 5. Риски

- **Повтор перф-регрессии журнала.** Любой компонент, добавленный НА строку, умножается на ~70
  видимых строк. Митигация — RA-D6 (один диалог на панель) + явная перф-проверка в RA1.6.
- **Расхождение условий доступности** между диалогом и нижней панелью. Митигация — RA-D4: одни и те
  же `computed` в обоих местах.
- **Модальный диалог мешает быстрому просмотру** нескольких записей подряд (раньше клик просто
  подсвечивал). Вынесено на приёмку RA1.7 — если мешает, вариант: открывать по двойному клику или
  по правой кнопке.
