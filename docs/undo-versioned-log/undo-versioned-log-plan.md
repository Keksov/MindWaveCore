## 3. Решения (VL-Dn)

- **VL-D1 (границы: сервер generic, семантика у клиента).** Новый серверный модуль
  `MindWaveCore/server/version-log-store.ts` — универсальный append-only лог КОММИТОВ с opaque
  payload; GTrack-семантику (voice-дельты, снапшоты расписания, реконструкцию состояния) сервер НЕ
  знает — она остаётся в `gtrack-model.ts`. Хранение — в папке проекта `<projectDir>/undo-log/`;
  project-store делегирует (id-валидация, SerialQueues, projectsRoot — переиспользуются).
- **VL-D2 (модель данных).** Коммит = `{seq, cid, parent, type: 'snapshot'|'delta'|'meta', atMs,
  payload}`. `cid` — клиентский стабильный id (уже есть: `GTrackUndoStep.id`); `parent` — cid
  родителя (null у корня); `seq` — серверный монотонный номер записи. Лог append-only: коммиты
  никогда не изменяются; «линейная история» = цепочка parent-ссылок от ref `main`; позиция курсора
  undo = ref `head` (аналог git HEAD); именованные метки — refs `tags{имя→cid}` (VL-D9). Правка
  после undo НЕ обрезает хвост: новый коммит получает
  `parent = head`, `main` переезжает на него, старый хвост остаётся в логе «орфаном» (недостижим от
  main) до GC. Линейный undo — частный случай git-модели (ровно как заложено в UG-D2); ветки/мерджи
  не реализуем, но модель их допускает.
- **VL-D3 (хранение).** NDJSON-сегменты `undo-log/seg-00000001.jsonl` (одна строка = один коммит;
  ротация по ~4 МБ) + `refs.json` `{main, head}` (мелкий, atomic-rewrite как весь project-store).
  Manifest/индекс НЕ нужен: имена сегментов упорядочены, состояние восстанавливается сканом
  (ленивый in-memory индекс на первом обращении). Восстановление: неполная последняя строка
  (torn write) отбрасывается и затирается следующим append; битая строка в середине — лог
  усекается до последней валидной, остаток уходит в `.broken-<ts>` (никогда молча не
  уничтожается — идиома project-store). Отклонено: `bun:sqlite` (бинарный, чужд прозрачной
  JSON-философии store, портит текстовый export-бандл), единый файл без сегментов (GC и чтение
  хвоста = полная перезапись/скан).
- **VL-D4 (протокол).** REST `/api/projects/undo-log*`, типы в `@protocol`:
  `POST …/append {id, commits[], advanceMain, gc?}` (идемпотентно по cid: дубликат = skip;
  неизвестный parent → 409 — клиент перечитывает лог), `GET …?id&from&limit&untilType`
  (цепочка от `from` (cid|'main'|'head') назад по parent), `POST …/refs {id, main?, head?}`
  (валидирует существование cid; last-write-wins), `POST …/clear {id}`. Лимит 5 МБ на лог НЕ
  применяется — только санити-лимит `VERSION_LOG_COMMIT_MAX_BYTES = 32 МБ` на ОДИН коммит (413).
  GC-политику передаёт клиент в `append.gc` (настройки живут в localStorage — сервер stateless).
- **VL-D5 (снапшоты и адопция).** Снапшот-коммит (`type:'snapshot'`, payload = полное расписание +
  сигнатура) пишет клиент: при каждом Save и каждые K=50 дельт без Save. Адопция на старте =
  `GET untilType=snapshot` (хвост от main до ближайшего снапшота) → реконструкция окна истории;
  сигнатурный гейт (currentSig/baseSig-семантика) сверяет снапшот с файлом. Ключевое отличие от
  v3: несовпадение сигнатур ≠ потеря — лог остаётся на сервере целиком, панель может показать
  прошлые версии и восстановить любую (checkout).
- **VL-D6 (GC).** Политика — существующие настройки «Журнал Undo» (maxSteps/maxAgeDays/maxSizeKb;
  по умолчанию 0 = хранить всегда; clearOnClose → `clear`). Порядок: сначала орфаны (недостижимые
  от main И head), затем префикс main-цепочки старше самого нового снапшот-якоря, укладывающего
  цепочку [якорь..main] в лимиты. Инвариант: после GC main-цепочка всегда начинается со снапшота;
  реконструируемость всех оставшихся коммитов не меняется. Запускается сервером после append
  (когда политика передана и нарушена). **Уточнение (квиз VL0.2):** при миграции клиент сбрасывает
  сохранённые лимиты в 0 («хранить всегда») с предупреждением — старое значение вроде
  «Макс. операций = 5» не должно тихо срезать глубокую историю (VL4.2).
- **VL-D7 (спека-как-тесты — req 1).** Раздел 4 (S1..S15) — ЕДИНСТВЕННЫЙ критерий приёмки фаз
  1–4: каждый инвариант закрыт автотестом (юнит + property/fuzz с детерминированными сидами и
  in-memory оракулом + байтовые краш-инъекции). Фазы 1–4 закрываются зелёным `bun test` БЕЗ
  участия владельца; владелец смотрит только финальную приёмку в приложении (VL5.2). Логика,
  которую нельзя автотестировать (Vue-синглтоны, fetch), выносится в чистые функции-планировщики,
  тестируемые отдельно. **Формат (квиз VL0.2):** после каждой фазы — короткий отчёт владельцу
  (что сделано, закрытые инварианты, счётчик тестов) БЕЗ остановки работ.
- **VL-D8 (миграция + полное удаление legacy; владелец, квиз VL0.2).** Миграция одноразовая,
  клиентская: лог пуст + есть валидный `undo.json` v3 → адоптировать v3 в память (текущий код),
  первый persist пишет в лог снапшот текущего состояния + дельты + meta `imported-v3`; после
  подтверждённого append клиент удаляет `undo.json`. Затем legacy удаляется ПОЛНОСТЬЮ (VL4.4):
  роуты GET/PUT `/api/projects/undo`, `UndoFileData`/`UNDO_FILE_NAME`/`UNDO_JOURNAL_MAX_BYTES`
  (5МБ-лимит исчезает вместе с ними), поле `undo` export-бандла → бандл переводится на
  `undoLog: {commits, refs}` (round-trip — S15). Осознанное следствие (подтверждено): старая
  версия UI журнал этого проекта больше не прочитает; формат export-бандла меняется.
  `ProjectInfo.undoJournalBytes` отражает размер `undo-log/` (+ остаточный undo.json до миграции),
  чтобы кэш-менеджер (UG4.2) продолжал показывать правду.

- **VL-D9 (метки; владелец, квиз VL0.2 — «Лог + checkout + метки»).** Именованная метка = запись в
  `refs.tags` (имя → cid), создаётся/удаляется из панели, переход = тот же checkout. Метка — корень
  GC: помеченный коммит и его цепочка до якоря не вычищаются (S8), даже если стали орфанами.
  Имена меток — как имена секций (`^[a-zA-Z0-9_-]{1,64}$` + кириллица? — берём паттерн шире:
  непустая строка ≤ 64 символов без управляющих); хранение в refs.json тривиально. UI — фаза 5.

## 4. Спецификация (контракт автотестов; VL-D7)

### 4.1 Модель данных

```
Commit   = { seq: number,           // серверный, монотонный внутри лога, уникальный
             cid: string,           // клиентский стабильный id, уникальный в логе
             parent: string | null, // cid существующего коммита; null только у корневого
             type: 'snapshot' | 'delta' | 'meta',
             atMs: number,          // клиентское время создания
             payload: unknown }     // opaque JSON; сервер не интерпретирует
Refs     = { main: string | null, head: string | null,
             tags: Record<string, string> }               // все значения — cid существующих коммитов
State    = { commits: Commit[], refs: Refs }              // наблюдаемое состояние лога
```

Достижимость: `reach(c)` = множество коммитов по parent-цепочке от c до корня. Корни GC —
`{main, head} ∪ values(tags)`. Орфан — коммит, не достижимый ни от одного корня.

### 4.2 Инварианты (S1..S15)

- **S1 (append-only).** Успешный `append` только добавляет коммиты; никакая операция, кроме `gc`
  и `clear`, не удаляет и не изменяет записанные коммиты (payload, parent, type, atMs, cid
  неизменяемы навсегда).
- **S2 (идемпотентность).** Повторный `append` коммита с уже известным cid — no-op для лога
  (skip, отражён в ответе); состояние после двойной отправки байт-в-байт равно состоянию после
  одинарной.
- **S3 (целостность цепочки).** У каждого коммита в логе `parent` = cid коммита, записанного
  ранее (или null). `append` пачки применяется атомарно по префиксу: коммит с неизвестным parent
  (не в логе и не раньше в пачке) → пачка режется до него, остаток отвергается с 409, лог
  содержит ровно принятый префикс.
- **S4 (порядок).** `seq` присваивает сервер; строго возрастает в порядке записи; никакие два
  коммита не делят seq (в т.ч. при параллельных append). После GC допустимы дыры, порядок
  сохраняется.
- **S5 (refs).** `main`/`head`/каждая метка — всегда cid существующего коммита (main/head могут
  быть null); `putRef` на неизвестный cid → 404, refs не меняются; удаление метки (значение null)
  допустимо и удаляет только её. `append(advanceMain)` двигает main на последний принятый коммит;
  head и метки не трогает (ими управляет клиент).
- **S6 (краш-устойчивость хвоста).** Для лога из N коммитов и ЛЮБОГО байтового префикса
  последней записанной строки: повторное открытие даёт валидное состояние с ≥ N-1 коммитами
  (потерян максимум оборванный хвост), все инварианты S1–S5 выполняются, последующий append
  продолжает лог без мусора между записями.
- **S7 (tolerant read).** Битая строка НЕ в хвосте (повреждение диска): лог усекается до
  последней валидной позиции до неё, отрезанное сохраняется в `seg-*.broken-<ts>`, ошибка
  логируется; store остаётся работоспособным (append/чтение). main/head, указывающие на
  отрезанные cid, сбрасываются на новейший выживший коммит (или null); метки на отрезанные
  cid удаляются.
- **S8 (GC-гарантии).** После `gc(policy)`: (а) орфаны (недостижимые ни от одного корня —
  main/head/меток) удаляются первыми; (б) main-цепочка от якорного снапшота до main сохранена
  целиком и начинается со снапшота; (в) якорь — самый новый снапшот, укладывающий цепочку
  [якорь..main] в лимиты (если даже минимальная цепочка [последний снапшот..main] лимит
  превышает — остаётся она: GC никогда не оставляет лог без якоря); (г) `reach(head)` и цепочки
  всех меток внутри сохранённого диапазона не тронуты — помеченный коммит не вычищается никогда;
  (д) payload сохранённых коммитов байт-в-байт неизменен.
- **S9 (реконструкция).** Для любого сохранённого delta-коммита c из main-цепочки:
  `apply(snapshot_anchor, deltas(anchor..c])` даёт одно и то же состояние до и после
  gc/reopen/crash-recovery. (Generic-часть — эквивалентность цепочек до/после; GTrack-часть —
  тесты реконструкции реальным `gtrack-model` в ui.)
- **S10 (лимиты).** Размер лога НЕ ограничен сервером (ни 5 МБ, ни иное) — только политика GC.
  Один коммит > `VERSION_LOG_COMMIT_MAX_BYTES` (32 МБ) → 413, лог не изменён.
- **S11 (конкурентность).** Параллельные операции над одним проектом сериализуются
  (SerialQueues): итог эквивалентен НЕКОТОРОМУ последовательному порядку тех же операций;
  разные проекты независимы.
- **S12 (clear).** `clear` приводит лог в начальное состояние (пустой список, refs=null);
  последующий append начинает новый корень.
- **S13 (сессионная эквивалентность).** Сценарий «сессия A: append дельт+снапшот; рестарт;
  сессия B: чтение untilType=snapshot» даёт B ровно тот хвост, который записала A (cid, порядок,
  payload); undo/redo между сессиями выражаются только движением head и не теряют коммитов.
- **S14 (миграция v3).** Планировщик миграции: (пустой лог, валидный v3) → последовательность
  append'ов (снапшот + дельты + meta 'imported-v3') + удаление undo.json ПОСЛЕ подтверждённого
  append; (непустой лог | битый v3) → миграции нет, v3 не удаляется (битый уходит в `.broken-*`
  существующим механизмом). Двойной запуск планировщика не дублирует историю (следствие S2).
- **S15 (export/import round-trip).** Экспорт проекта сериализует лог в бандл
  (`undoLog: {commits, refs}`); импорт восстанавливает состояние лога байт-в-байт (payload, cid,
  parent, refs, метки), включая пустой лог и лог с орфанами. Инварианты S1–S5 выполняются на
  импортированном логе.

## 6. Риски

- **Размер снапшотов.** Полное расписание большого пресета — сотни КБ; частота (Save + каждые 50
  дельт) удерживает долю снапшотов малой, GC по настройкам страхует. Отдельно: snapshot НЕ
  уходит в keepalive-flush (64 КБ лимит браузера) — только обычным fetch.
- **Две вкладки.** append безопасен всегда (обе цепочки сохраняются); refs — last-write-wins
  (осознанно, как весь project-store PR-D7). Реальность приложения — один webview.
- **server.ts NUL-байт** (~offset 10862) — только точные Edit-правки, поиск `rg --text`;
  тесты серверную логику берут из модуля, роуты остаются тонкими.
- **CRLF** в use-project.ts/project-api.ts — править Edit'ами, не скриптами (memory-правило).
- **Windows-rename** при GC-перезаписи сегментов: писать новый файл + rename только при
  закрытых дескрипторах (append каждый раз открывает/закрывает — держать это свойство).
- **Legacy-двоевластие** undo.json vs undo-log на переходный период: разрешено только чтение
  legacy; единственный писатель нового клиента — undo-log (S14 удаляет v3 после миграции).
