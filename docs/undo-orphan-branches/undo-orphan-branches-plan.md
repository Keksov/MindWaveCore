# undo-orphan-branches — просмотр, восстановление и удаление орфан-веток

Кандидат №2 из финального отчёта `undo-versioned-log`. Модель лога хранит «отменённые будущие»
(правка после undo форкает историю, старый хвост остаётся орфаном — VL-D2 «Хранить»), но доступа
к ним нет: панель ходит только по parent-цепочке от `main`. В реальном `wakeup` из 45 коммитов
достижимы 24 — половина истории невидима и недоставаема. Эта фича даёт секцию «Ветки» в панели
журнала: перечисление, просмотр шагов, восстановление через checkout, метки и ручное удаление.

## 1. Требования владельца (дословно)

1. (2026-07-21) «go 2.» — старт кандидата №2: «Просмотр/восстановление орфан-веток в панели
   (хвост вашей проверочной сессии раунда 2 так и лежит орфаном на диске)».
2. Квиз OB0.1 (2026-07-21), «Под-ветки»: **«Плоский список верхушек»** — каждая верхушка
   недостижимой цепочки = отдельная строка; общий префикс виден при просмотре каждой.
3. Квиз OB0.1 (2026-07-21), «Восстановл.»: **«Checkout на текущую линию»** — «Применить» кладёт
   состояние новым обычным коммитом (механизм VL5.1), Ctrl-Z откатывает, ветка остаётся.
4. Квиз OB0.1 (2026-07-21), «Чистка»: **«Сделать в этой фиче»** — кнопка «Удалить ветку» с
   подтверждением; физически удаляются только эксклюзивные коммиты верхушки (общий префикс
   под-веток остаётся), помеченная ветка — отказ; через механизм GC-перезаписи.

## 2. Контекст (что уже есть)

- `version-log-store.ts`: `collectReachable` (:748, main+head+tags), `stats().orphans`,
  GC-перезапись `runGc` (:720 — temp `.seg-gcnew-` → rename-over seg-1 → rm остальных → drop
  cache → reload; краш-безопасность через load-каскад), `LogState` {commits: Map, order[]}.
- REST: `GET /api/projects/undo-log?id&from&limit&untilType` (цепочка от cid|main|head),
  `POST /api/projects/undo-log/append|refs|clear` (server.ts :1447/:1483).
- Клиент: `checkoutUndoCommit(cid)` (use-gtrack-lanes :855) уже реконструирует состояние от
  ЛЮБОГО cid — цепочка от верхушки орфана сама проходит развилку вниз до снапшота; deepRowOfCommit
  (:810) — готовый маппер коммит→строка; метки setUndoTag/deleteUndoTag; панель UndoJournalPanel.
- Диск-доказательство (wakeup, 2026-07-21): 45 коммитов, 21 орфан, 4 верхушечные группы
  (Б1 12:18 ×1, Б2 12:20 ×1, Б3 12:30–19:00 ×11 с 3 под-ветками от общего снапшота,
  Б4 19:02–19:03 ×8 с 2 снапшотами).

## 3. Решения

- **OB-D1 (квиз — плоско).** Ветка = верхушка (tip): орфан-коммит без детей. Строка списка = tip;
  цепочка ветки = tip→…→forkParent (не включая), общий префикс под-веток входит в каждую из них.
  Сортировка — новые сверху (по seq верхушки).
- **OB-D2 (квиз — checkout).** «Применить» на шаге ветки = существующий `checkoutUndoCommit(cid)`
  без изменений: обычный undo-able коммит на текущей линии; лог и ветка не переписываются.
- **OB-D3 (квиз — удаление).** `deleteBranch(tip)`: удаляется ровно эксклюзивный суффикс — walk
  от tip вниз, пока коммит недостижим от линии И является единственным ребёнком; стоп на
  fork-коммите (≥2 детей) или line-достижимом. Метка на любом коммите эксклюзивного суффикса →
  409, лог не тронут (снимите метку — удалится). Графтов не возникает по построению (удаляемое
  множество замкнуто по детям) — это assert. Механика — общий с GC хелпер перезаписи
  (atomic rename + drop cache + reload); сериализация SerialQueues (S11).
- **OB-D4 (две достижимости).** Список веток считается от **{main, head}** — БЕЗ меток: иначе
  помеченная ветка исчезала бы из списка в момент пометки. Защита от GC остаётся прежней
  ({main, head, tags} — S8 не меняется). Метки на коммитах ветки показываются бейджами строки.
- **OB-D5 (транспорт).** `GET /api/projects/undo-log/branches?id` →
  {id, branches: ProjectUndoLogBranch[]}; `POST /api/projects/undo-log/delete-branch` {id, tip} →
  {id, deleted} | 404 | 409. Сводка ветки: {tip, forkParent: cid|null, commits (длина цепочки над
  forkParent), exclusiveCommits, fromMs, toMs, snapshots, tags[]}. Просмотр ветки — существующий
  GET from=tip&limit=commits (нового чтения не нужно).
- **OB-D6 (спека-как-тесты, стиль VL-D7).** Раздел 4 — критерий приёмки фаз 1–2; UI (фаза 3)
  принимает владелец на живом wakeup (PAUSE OB3.2).

## 4. Спецификация B1..B9

- **B1 (разбиение).** Каждый коммит лога либо достижим от {main, head}, либо принадлежит цепочке
  хотя бы одной ветки из listBranches; в списке нет line-достижимых коммитов.
- **B2 (верхушки).** У tip нет детей; никакой tip не предок другого tip; каждый орфан-коммит без
  детей — в списке ровно один раз.
- **B3 (forkParent).** forkParent — ближайший line-достижимый предок верхушки, либо null
  (обрыв/graft-корень); он сам в цепочку ветки не входит.
- **B4 (сводка).** commits/exclusiveCommits/fromMs/toMs/snapshots/tags точно соответствуют
  цепочке tip→forkParent (tags — метки, указывающие на коммиты цепочки).
- **B5 (эксклюзивность удаления).** deleteBranch удаляет ровно эксклюзивный суффикс: другие ветки
  и линия читаются как прежде (побайтно те же коммиты, seq сохранены); tip исчезает из списка;
  общий префикс остаётся (осиротевший префикс без детей сам становится новой верхушкой).
- **B6 (защита меткой).** Метка на коммите эксклюзивного суффикса → 409 и лог байт-в-байт не
  изменён; метка на общем префиксе удалению не мешает.
- **B7 (краш-безопасность).** Удаление идёт через тот же rewrite-хелпер, что GC (S6/S7/S8-тесты
  покрывают восстановление); дополнительно: delete → forget → reload сходится к тому же состоянию.
- **B8 (fuzz).** Оракул расширяется: (а) после каждой операции разбиение B1/B2 сверяется со
  store.listBranches; (б) новая операция deleteBranch случайной верхушки зеркалится в оракуле,
  listCommits/refs сравниваются. Все существующие сиды остаются зелёными.
- **B9 (конформанс E2E).** Реальная сессия GTrackModel: правки → undo×2 → новая правка (форк) →
  «рестарт» (forget): listBranches находит хвост (2 шага), checkout верхушки возвращает состояние
  с сигнатурой хвоста, deleteBranch убирает его; окно и линия не пострадали.

## 6. Риски

- Гонка «удалили ветку, на которую смотрим»: раскрытая цепочка держится по cid — после delete
  обновляем список и сбрасываем раскрытие; checkout исчезнувшего cid вернёт 404 → 'failed' notify.
- Много верхушек в патологическом логе: сводки маленькие, отдаём все; страница шагов ветки — уже
  постраничный GET. Если станет проблемой — лимит вторым заходом.
- Правка server.ts (NUL-байт): только точечные Edit, поиск rg --text.
- use-gtrack-lanes.ts — CRLF: perl-проверка после каждой правки.
